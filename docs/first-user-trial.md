# First outside-developer trial

Status on September 20, 2026: **not conducted**. No participant, outreach, elapsed-time result, quote, adoption or customer defect is claimed. DispatchDesk and automated agent reviews are separate synthetic/engineering evidence.

This is a short protocol for a developer who did not build ReplayGuard. It requires an available participant and permission before publishing their identity, recording, quote or source. No outreach is authorized by this document.

## Task and observation

Allow 25–35 minutes. Give the participant the public README/kit and the [runbook](repair-lab/runbook.md), not a privately prepared success environment. Use trusted code and synthetic inputs; do not request credentials or production/customer data.

1. Start timing when the participant receives the materials. Record their OS and Python version and the exact kit hash/version.
2. Ask them to run a supported passing case and explain what the result establishes.
3. Ask them to change the adapter's key, rerun the same case, inspect the affected order and restore the repair. Record every hint, failure and retry without resetting the clock.
4. If they have suitable independently developed Python worker code they may safely use, attempt an adapter and record the changes needed. Otherwise stop at onboarding; do not call the prepared example an existing-application integration.
5. Ask what they believe the observer proves, what remains outside the effect contract, and where they became stuck. Obtain permission before quoting their answer.

Targets for diagnosing friction are a first pass within five minutes and an edited failure/restored pass within fifteen. These are targets, not observed results or productivity claims. A missed target is useful evidence and must remain recorded.
